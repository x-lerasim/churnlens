# ChurnLens

Интеллектуальная система поддержки бизнес-аналитика для прогнозирования и предотвращения оттока клиентов.

Предметная область: SaaS-платформа для средств размещения (PMS, менеджер каналов, модуль бронирования, RMS). Клиент = объект размещения, оплата подписки за номер. Отток = объект перестал платить и отключился. Все данные синтетические.

## Структура

```
docker-compose.yml     ClickHouse, лимит памяти 4 ГБ
docker/clickhouse/     настройки памяти сервера и запросов
sql/raw/               DDL сырого слоя
data/generator/        генератор синтетики (config.py: все параметры)
data/loader/           загрузка parquet в ClickHouse
data/checks/           проверки после загрузки
data/output/           сгенерированные parquet (не в git)
ml/ backend/ frontend/ docs/   следующие этапы
```

## Запуск

Нужны Docker и Python 3.11+.

```bash
cp .env.example .env
docker compose up -d

python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python -m data.generator.generate
python -m data.loader.load --recreate
python -m data.checks.check
```

Генерация занимает около 15 секунд, загрузка около 10 секунд.
`--recreate` удаляет базу `raw` и создаёт таблицы заново.

ClickHouse: http://localhost:8123/play, пользователь и пароль `churnlens`.

## Сырой слой (база raw)

| таблица | строк | что лежит |
|---|---|---|
| clients | 5 000 | объект: тип, регион, номерной фонд, дата подключения, канал привлечения, наличие аккаунт-менеджера |
| subscriptions | ~5 300 | история тарифов, статус, дата и причина отключения |
| modules | ~17 700 | подключение и отключение модулей |
| activity_daily | ~2.8 млн | логины, пользователи, действия в шахматке, обновления цен, ошибки синхронизации |
| bookings | ~5.8 млн | бронирования по дню и каналу продаж |
| support_tickets | ~186 000 | обращения в поддержку, категория, приоритет, CSAT |
| payments | ~70 000 | счета и оплаты |

Метка оттока хранится только в `subscriptions` (`status = 'cancelled'`, `end_date`), в карточке клиента её нет, чтобы признаки не «знали будущее».

## Логика генератора

- 5000 объектов, период 2024-09-01 по 2026-08-31, seed 42.
- 72% клиентов подключены до начала периода, 28% приходят в течение периода.
- Риск ухода зависит от типа объекта, размера, стажа, числа модулей, тарифа, периода оплаты, канала привлечения и аккаунт-менеджера. Плюс случайная скрытая компонента. Базовый уровень калибруется на годовой отток 12.5%.
- Уходящие делятся на два типа:
  - постепенный уход (72%): за 30-90 дней падает активность и бронирования, растут тикеты (биллинг, баги, синхронизация), задерживаются оплаты, отключаются модули, иногда даунгрейд тарифа;
  - внезапный уход (28%): продажа или закрытие объекта, сигналов почти нет.
- Ложные сигналы у остающихся: временные провалы активности (10% клиентов), хронически поздние плательщики (8%), случайное отключение модулей.
- Сезонность: глэмпинги и базы отдыха зимой проседают в 2-3 раза, морские регионы пик летом. Это не отток.

## Результат проверки

- годовой отток 12.5%, по месяцам 0.7-1.5%;
- по типам: глэмпинги ~19%, гостевые дома и апартаменты ~16%, отели ~8.5%;
- причины: переход к конкуренту, неоплата, закрытие объекта, функциональность, продажа объекта, цена.
